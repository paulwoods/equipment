# 3. JWT access token + opaque refresh token, both as HttpOnly cookies

- **Status:** Accepted (reverse-engineered)
- **Date:** 2026-05-06

## Context

The frontend is a browser-based SPA on the same registrable domain as the API
(production: a single domain reverse-proxied by Caddy; development:
`localhost:5173` ↔ `localhost:8080` via CORS). Authentication needs to:

1. work without prompting users to copy/paste tokens or store secrets in
   `localStorage` (which is reachable from any XSS),
2. survive page reloads and tab restores,
3. allow short-lived access credentials but smooth re-auth.

## Decision

Use a **two-token scheme delivered exclusively as cookies**:

- **`access_token`** — a signed JWT (HS256 via JJWT 0.13), 1-hour default
  TTL, claims include `sub` (email) and `roles`. Generated by
  `JwtService.generateToken`.
- **`refresh_token`** — an opaque UUID v4 stored in the `refresh_token`
  table, 7-day TTL, used only to mint new access tokens.

Cookie attributes set by `CookieService`:

- `HttpOnly`, `Secure` (toggleable via `APP_COOKIE_SECURE` for local dev),
  `SameSite=Lax`.
- Access cookie path `/`; refresh cookie path **`/api/v1/auth`** so it is
  only sent on auth endpoints.

The JWT secret must be at least 32 bytes — enforced by `JwtSecretValidator`
at startup.

## Consequences

- **Positive:** tokens are unreachable from JavaScript, blunting XSS-driven
  token theft.
- **Positive:** refresh-token scoping means the long-lived credential is
  never sent to business-logic endpoints.
- **Negative:** CSRF protection is now mandatory for state-changing
  endpoints. The current code disables Spring Security's CSRF filter and
  relies on `SameSite=Lax` cookies plus CORS allow-list to prevent
  cross-origin posts. This works for `Lax`-compatible browsers but is
  weaker than a token-based defence — flag for review if a third-party
  embedder is ever introduced.
- **Negative:** SPA cannot read its own auth state directly; it must call
  `GET /api/v1/auth/me` on load (see `App.tsx`).
- **Tradeoff:** revoking an access token before its 1-hour expiry is not
  possible — we accept this in exchange for stateless validation. Refresh
  tokens *can* be revoked because they are stored.
