Collapse three rate limiters into one deep module

Strong in-process

service/LoginRateLimiterService.java · service/ForgotPasswordRateLimiterService.java · filter/ApiRateLimitFilter.java

Before — three shallow copies

  C["ApiRateLimitFilter\nCaffeine cache (ip)"]
  classDef dup fill:#fef2f2,stroke:#dc2626,stroke-width:1px;

After — one deep module

flowchart TB
  R["RateLimiter\ntryConsume(key, window, max)"]:::deep
  L[LoginRateLimiterService] --> R
  F[ForgotPasswordRateLimiterService] --> R
  A[ApiRateLimitFilter] --> R
  classDef deep fill:#0f172a,color:#fff,stroke:#0f172a;

Problem: the same counter-window behavior — cache a count per key, expire after a window, block over a threshold — is implemented independently three times, each with its own Caffeine.newBuilder() and increment logic.

Solution: one RateLimiter module with a two-method interface (tryConsume, reset); the three call sites become configuration, not reimplementation.

  • Locality: the counting algorithm changes once, not three times
  • Leverage: one interface, three call sites
  • Three duplicate implementations are the proof this seam is real, not hypothetical

After — tier named once

  Boot2["AdminBootstrap\n(advisory-lock setup)"]

Problem: UserService mixes first-run bootstrap (Postgres advisory lock), plain CRUD, self-service profile/password changes, and role-tier authorization checks called separately from create/update/delete. Meanwhile the tier membership itself — which roles a caller may manage — is copy-pasted as literal SpEL strings across 5 controllers (12 occurrences of two tier strings).

Solution: pull the tier concept (ADR-0028's tiers, today implicit in string literals and assertCallerCanManageRole) into one small module callers reference by name; separate the advisory-lock bootstrap into its own module.

Doesn't contradict ADR-0028 (method-level @PreAuthorize stays) — this only names the tiers it already encodes.
  • Locality: tier membership defined once, not 12 places
  • Leverage: one authorization interface for every check
  • UserServiceTest (602 lines, 6 mocked collaborators) shrinks along with the interface

Query Procedure/Perform directly instead of scanning the Equipment aggregate

Worth exploring ports & adapters

service/ProcedureService.java:34-40 · service/PerformHistoryService.java:22-38 · repository/{Procedure,Perform}Repository.java

Before — three hops, full aggregate each time

sequenceDiagram
  participant Ctl as PerformHistoryController
  participant PH as PerformHistoryService
  participant PS as ProcedureService
  participant ES as EquipmentService
  Ctl->>PH: getHistory(equipmentId, procedureId)
  PH->>PS: getEntityById(equipmentId, procedureId)
  PS->>ES: getEntityById(equipmentId)
  ES-->>PS: full Equipment (all procedures)
  PS->>PS: linear scan for procedureId
  PS-->>PH: Procedure
  PH->>PH: read .getHistory()

After — one direct query

sequenceDiagram
  participant Ctl as PerformHistoryController
  participant PH as PerformHistoryService
  participant Repo as PerformRepository
  Ctl->>PH: getHistory(equipmentId, procedureId)
  PH->>Repo: findByProcedureId(procedureId)
  Repo-->>PH: history rows

Problem: fetching one Perform history record requires controller → PerformHistoryService → ProcedureService → EquipmentService, each re-loading the whole Equipment aggregate and linear-scanning its collections to find one Procedure by id — the lookup path is only visible by reading three files together.

Solution: give ProcedureRepository/PerformRepository direct finder methods so each service queries what it needs instead of walking the aggregate through two other services.

  • Locality: one query per lookup, not three service hops
  • Leverage: the repository seam carries the lookup instead of a hand-rolled scan

Give the dashboard email's HTML-building its own testable seam

Worth exploring mock

service/EmailService.java:76-115 (buildHtml, buildTableRow) · test/.../EmailServiceTest.java

Before — real logic hidden behind a void send

public sendDashboardEmail() — the only seam

Tests only assert verify(mailSender).send(any()) — never inspect the HTML produced.

After — pure module, direct seam

Problem: the one piece of real logic — status-based row coloring, date formatting, raw string interpolation with no HTML escaping — sits in private methods behind a void, side-effecting send. Tests can only verify the send happened, not what was sent.

Solution: extract a pure render(items) → String module; EmailService keeps only the JavaMailSender call.

  • The interface becomes the test surface — no mocking JavaMailSender to check content
  • Locality: HTML bugs (e.g. missing escaping) fixed and verified in one place

Top recommendation

Collapse three rate limiters into one deep module

Self-contained in the backend, no cross-cutting UI changes, and the seam is already proven real — three independently-written implementations of the same counter-window behavior is stronger evidence than the usual "two adapters" bar. Lowest risk, cleanest locality payoff, good first cut before touching the higher-surface-area User module.
